# Phase 3 · Plan 01 — Tracer: End-to-End Repository Slice (schema + write + read + two-org isolation)

## User Story (MVP framing per ROADMAP Phase 3 Goal)

**As a** buyer using SourceGPT to discover suppliers across multiple events,
**I want to** have suppliers I discovered in one event persist in a durable, org-scoped repository that survives the event, is deduped against my prior discoveries, and is structurally isolated from other organizations' private data,
**so that** my organization builds an accumulating asset of vetted suppliers over time without leaking any of my private enrichment, AI-score, notes, or rating data to any other organization.

## Assumption-delta decision (recorded per contribution#assumption-delta detector)

**Signal:** pluralization — REPO-04's "another org's private enrichment/AI-score/notes" surfaces a second-org case that the pre-existing supplier model did not accommodate.

**Decision:** **promote** — the ownership noun for private supplier data is promoted from `(supplier)` to `(org_id, supplier_identity)`. Concretely, `enrichment`/`ai_score`/`notes`/`rating` — which previously lived only on the per-event `suppliers` table implicitly scoped via `suppliers.event_id -> sourcing_events.org_id` — are now first-class org-scoped columns on a new `org_supplier_data` table with a direct `org_id` foreign key. The identity itself (`supplier_identities`) also carries a direct `org_id` column, so per-org uniqueness (`UNIQUE (org_id, norm_name)`) is enforced at the schema level and identical company names discovered independently by two different orgs deliberately produce two separate identity rows (REPO-06, D-05).

**Rationale:** This is the structural isolation REPO-04 explicitly asks for — a leaky query scoped to `supplier_identities` alone cannot expose private fields (they aren't columns on that table), which no amount of query-discipline auditing can guarantee under the old shared-table model. The `add-alongside` alternative (keeping `enrichment`/`ai_score` on the per-event `suppliers` table AND mirroring into a new table) was rejected: it doubles the write-path complexity without gaining structural isolation, since a query bug against the old table would still leak.

**Reversibility rating:** **one-way** — merging the two tables back after data has accumulated would require a schema migration (data-preserving DDL + application code changes) rather than a config toggle. A `checkpoint:decision` gate is inserted before Task 1 (schema DDL) below.

## Objective

Wire one production-quality end-to-end path from **schema DDL creation** through **write-path integration at ONE call site** (`makeProcessSupplier()` — full-investigation only, the highest-value discovery path) to **org-scoped read** with a **live two-org isolation test that runs and passes**. This is the tracer per TRACER_MODE — the thinnest complete vertical slice that touches every layer this phase modifies, proving the architecture end-to-end before Plan 03-02 expands the write path to `makeProcessSupplierQuick()`/`makeProcessSupplierDeepen()` and Plan 03-03 adds the REPO-05 pre-search read path.

**Purpose:** Prove the entire multi-tenant supplier-repository architecture (structural isolation via two-table split + `WHERE org_id=?` filter + `ON CONFLICT` upsert + best-effort side write) on ONE call site with a real test, so any architectural dead-end is caught after one plan instead of after four.

**Output:** A committable slice where a full-investigation discovery of a supplier persists into the repository, is dedup-safe on re-discovery, is structurally impossible to leak across orgs, and has an explicit two-org test proving it.
